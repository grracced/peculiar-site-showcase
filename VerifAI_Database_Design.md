# VerifAI - Logical Database Design Specification

> **Lead Database Architect Note:**
> This document details the logical database architecture for the VerifAI MVP. Following the TDR, the target database is PostgreSQL (managed via Supabase) accessed via Prisma. This schema is strictly relational, normalized to 3NF where appropriate, and optimized for write-heavy background jobs (Hedera/AI) and read-heavy user dashboards. 
> 
> *Note: No SQL or Prisma schema code is included here. This is the logical blueprint.*

---

## 1. Database Overview

- **Chosen Database:** PostgreSQL (Relational).
- **Why it was chosen:** VerifAI's data is highly structured. A user *has many* documents; a document *has one* verification record. Relational integrity is paramount when dealing with cryptographic audit trails. PostgreSQL provides strict ACID compliance, essential for data correctness in a Web3/SaaS context.
- **Design Principles:**
  - **Soft Deletes:** Critical entities (Users, Documents) are never hard-deleted to preserve referential integrity for audit logs.
  - **Normalization vs. Performance:** We use 3NF for most tables to avoid data anomalies. However, AI Analysis outputs may be stored as `JSONB` to accommodate varying AI provider schemas without altering our table structures.
- **Scalability Considerations:** Using UUIDs for all primary keys (instead of auto-incrementing integers) ensures that we can eventually shard the database across multiple servers if necessary without primary key collisions.

---

## 2. Entity Relationship Model (ERD)

### Entities & Relationships
1. **Users `1 : 1` User Profiles**
   - *Explanation:* Separates core authentication data from application-level user details.
2. **Users `1 : M` Documents**
   - *Explanation:* A user can upload many documents over time.
3. **Documents `1 : 1` AI Analysis**
   - *Explanation:* Each uploaded document undergoes one distinct AI extraction process.
4. **Documents `1 : 1` Verification Records**
   - *Explanation:* Each document results in exactly one cryptographic hash record.
5. **Verification Records `1 : 1` Hedera Transactions**
   - *Explanation:* The verification record is mapped to exactly one confirmed network transaction.
6. **Users `1 : M` Audit Logs**
   - *Explanation:* All major actions performed by a user are tracked.
7. **Users `1 : M` Notifications**
   - *Explanation:* Users receive multiple system notifications.
8. **Users `1 : M` Sessions**
   - *Explanation:* A user can be logged in on multiple devices.
9. **Users `1 : M` API Keys**
   - *Explanation:* (Future-ready) A user can generate multiple developer keys.
10. **Users `1 : M` Activity History**
    - *Explanation:* Tracks UI-level events (like logging in or downloading a report) distinct from strict security audit logs.

## 3. & 4. Table Design & Required MVP Tables

### 1. Users
- **Purpose:** Core identity table managed by Supabase Auth.
- **Columns:**
  - `id` (UUID, Primary Key)
  - `email` (String, Unique, Not Null)
  - `password_hash` (String, Not Null - *Managed internally by Supabase*)
  - `created_at` (Timestamp, Default NOW)
  - `updated_at` (Timestamp, Auto-updates)
  - `deleted_at` (Timestamp, Nullable)

### 2. User Profiles
- **Purpose:** Application-specific user data decoupled from strict Auth.
- **Columns:**
  - `id` (UUID, Primary Key)
  - `user_id` (UUID, Foreign Key -> Users.id, Unique)
  - `full_name` (String, Nullable)
  - `avatar_url` (String, Nullable)
  - `subscription_tier` (Enum: `FREE`, `PRO`, `ENTERPRISE`, Default `FREE`)
  - `created_at` (Timestamp, Default NOW)
  - `updated_at` (Timestamp, Auto-updates)
- **Indexes:** `idx_user_profiles_user_id`

### 3. Documents
- **Purpose:** Tracks the file uploaded by the user. Note: The actual file is deleted from Cloud Storage after processing to save costs and reduce liability, but this record persists.
- **Columns:**
  - `id` (UUID, Primary Key)
  - `user_id` (UUID, Foreign Key -> Users.id, Not Null)
  - `original_filename` (String, Not Null)
  - `mime_type` (String, Not Null)
  - `file_size_bytes` (Integer, Not Null)
  - `status` (Enum: `UPLOADING`, `PROCESSING_AI`, `HASHING`, `ANCHORING`, `VERIFIED`, `FAILED`)
  - `created_at` (Timestamp)
  - `deleted_at` (Timestamp, Nullable)
- **Indexes:** `idx_documents_user_id`, `idx_documents_status`

### 4. AI Analysis
- **Purpose:** Stores the extracted context and metadata generated by OpenAI/Gemini.
- **Columns:**
  - `id` (UUID, Primary Key)
  - `document_id` (UUID, Foreign Key -> Documents.id, Unique, Not Null)
  - `provider` (Enum: `OPENAI`, `GEMINI`)
  - `raw_json_output` (JSONB, Not Null) - *Provides flexible schema for AI outputs.*
  - `tokens_used` (Integer, Nullable) - *For internal cost tracking.*
  - `created_at` (Timestamp)

### 5. Verification Records
- **Purpose:** The core cryptographic proof of the document.
- **Columns:**
  - `id` (UUID, Primary Key)
  - `document_id` (UUID, Foreign Key -> Documents.id, Unique, Not Null)
  - `sha256_hash` (String, Not Null, Unique)
  - `created_at` (Timestamp)
- **Indexes:** `idx_verification_records_hash` (Crucial for the Public Verification Portal queries).

### 6. Hedera Transactions
- **Purpose:** Maps our internal Verification Record to the public Hedera ledger.
- **Columns:**
  - `id` (UUID, Primary Key)
  - `verification_record_id` (UUID, Foreign Key -> VerificationRecords.id, Unique)
  - `topic_id` (String, Not Null)
  - `transaction_id` (String, Not Null, Unique)
  - `consensus_timestamp` (Timestamp, Nullable) - *Updated once Mirror Node confirms.*
  - `network` (Enum: `MAINNET`, `TESTNET`)

### 7. Audit Logs
- **Purpose:** Strict, append-only security ledger for admin/user actions (e.g., "Deleted API Key", "Changed Password").
- **Columns:**
  - `id` (UUID, Primary Key)
  - `user_id` (UUID, Foreign Key -> Users.id, Not Null)
  - `action` (String, Not Null)
  - `ip_address` (String, Nullable)
  - `user_agent` (String, Nullable)
  - `created_at` (Timestamp)
- **Constraints:** Append-only logic enforced at the API layer.

### 8. Notifications
- **Purpose:** In-app alerts for users (e.g., "Document Verification Failed").
- **Columns:**
  - `id` (UUID, Primary Key)
  - `user_id` (UUID, Foreign Key -> Users.id, Not Null)
  - `type` (Enum: `INFO`, `SUCCESS`, `WARNING`, `ERROR`)
  - `message` (String, Not Null)
  - `is_read` (Boolean, Default False)
  - `created_at` (Timestamp)

### 9. Sessions
- **Purpose:** Track active user sessions. (Mostly handled by Supabase Auth internally, but modeled logically here).
- **Columns:** `id` (UUID), `user_id` (UUID), `refresh_token` (String), `expires_at` (Timestamp), `ip_address` (String).

### 10. API Keys (Future-ready)
- **Purpose:** Allow B2B developers to access the VerifAI API directly.
- **Columns:**
  - `id` (UUID, Primary Key)
  - `user_id` (UUID, Foreign Key -> Users.id, Not Null)
  - `key_name` (String, Not Null)
  - `api_key_hash` (String, Not Null) - *Keys are hashed, never stored in plain text.*
  - `last_used_at` (Timestamp, Nullable)
  - `expires_at` (Timestamp, Nullable)
  - `created_at` (Timestamp)

### 11. Activity History
- **Purpose:** Less strict than Audit Logs; used to populate the "Recent Activity" widget on the dashboard.
- **Columns:** `id` (UUID), `user_id` (UUID), `event_description` (String), `created_at` (Timestamp).

## 5. Data Lifecycle

- **Creation:** Data is generated via frontend interactions (e.g., uploading a file creates a `Document` row with status `UPLOADING`). Background jobs subsequently create `AI Analysis` and `Hedera Transaction` rows.
- **Updates:** Mostly restricted to `status` fields on the `Document` table and `is_read` on `Notifications`. Hedera rows are updated once when the Mirror Node confirms consensus.
- **Deletion (Soft Delete Strategy):** 
  - To maintain cryptographic integrity and audit trails, we employ **Soft Deletes**. 
  - When a user "deletes" a document from their UI, we set `deleted_at = NOW()` on the `Document` table.
  - Queries automatically filter out rows where `deleted_at IS NOT NULL`.
  - We do *not* delete the `Verification Record` or `Hedera Transaction` rows, as the public ledger is immutable anyway.
- **Archiving:** After 1 year, old Audit Logs and Notifications are moved to cold storage (e.g., AWS S3 CSV dumps) to keep primary database indexes fast.

## 6. Security

- **Sensitive Fields & Encryption:** 
  - `Users.password_hash` and `APIKeys.api_key_hash` are secured using bcrypt/Argon2. 
  - We do not store plain-text API keys; we show them to the user *once* upon generation.
- **Personally Identifiable Information (PII):** 
  - `email` and `full_name` are PII. We rely on Supabase's built-in AES-256 encryption at rest.
  - **CRITICAL:** `AI Analysis` `raw_json_output` may contain PII extracted from user documents. Therefore, the data sent to Hedera (`VerificationRecords.sha256_hash`) must **strictly be a hash**, never the raw JSON, to prevent leaking PII onto a public blockchain.
- **Access Control:** 
  - Row Level Security (RLS) must be enabled on every table. A user can only `SELECT`, `UPDATE`, or `SOFT DELETE` rows where `table.user_id = auth.uid()`.
  - The Public Verification API bypasses RLS for `VerificationRecords` strictly for exact-match hash lookups.

## 7. Scalability

The database is architected to scale linearly:

- **100 Users (MVP):** A single Supabase Postgres instance easily handles this. Default index on Primary Keys is sufficient.
- **1,000 Users:** We begin to see moderate read traffic on the Dashboard. Indexes on `user_id` across all tables (`Documents`, `History`, `Notifications`) ensure quick dashboard load times.
- **10,000 Users:** The `VerificationRecords` table will grow massive as users upload daily. We add a B-Tree index on `sha256_hash` to ensure the Public Verification Portal can find a match among millions of rows in milliseconds. We introduce PgBouncer (connection pooling) to handle the increased concurrent API connections.
- **100,000 Users (Enterprise):** 
  - The `Audit Logs` and `Activity History` tables become bloated. We implement Postgres Table Partitioning (partitioning logs by month) to maintain query speed.
  - We introduce a Read Replica database. Dashboard `SELECT` queries are routed to the replica, while heavy AI/Hedera background jobs write to the Primary database, preventing UI locking during massive background processing spikes.
